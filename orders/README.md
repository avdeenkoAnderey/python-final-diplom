# Сервис закупок: запуск собственной реализации

Код приложения находится в `orders/`, готовый учебный пример в `reference/` для запуска не нужен.

## Установка с нуля в Windows PowerShell

Нужны Git и Python 3.10 или новее. Команды ниже выполняются из корня клонированного `python-final-diplom`.

```powershell
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
cd orders
python manage.py migrate
python manage.py createsuperuser
python manage.py check
python manage.py runserver
```

Для входа суперпользователя используются email и пароль, указанные при `createsuperuser`.
Если активация окружения запрещена политикой PowerShell, активация не обязательна:
запускайте Python через `.\.venv\Scripts\python.exe` из корня репозитория
или `..\.venv\Scripts\python.exe` из папки `orders`.

- Админка: <http://127.0.0.1:8000/admin/>.
- Каталог: <http://127.0.0.1:8000/api/v1/products>.
- Регистрация покупателя: <http://127.0.0.1:8000/api/v1/user/register>.
- Описание методов и примеры запросов: [API.md](API.md).

Пустой путь `/` не подключён: используйте адреса выше. При переходе браузером на POST-метод
ответ 405 ожидаем — запрос нужно отправлять формой POST в интерфейсе DRF или HTTP-клиентом.

## Начальный каталог

1. В админке создайте отдельного пользователя с типом «Поставщик» и активной учётной записью.
2. Из папки `orders` загрузите прайс, подставив email этого пользователя:

```powershell
python manage.py import_catalog ../data/shop1.yaml --email "supplier@example.com"
```

Команда создаст магазин поставщика и загрузит товары. Повторный импорт обновляет существующие предложения.
Магазин заранее создавать не нужно. Альтернативный путь — загрузка файла через `POST /api/v1/partner/update`
с токеном поставщика; пример приведён в `API.md`.

## Покупка

Зарегистрируйте покупателя через API, подтвердите email токеном из письма и выполните вход.
С токеном входа создайте адрес, добавьте предложения в корзину и оформите заказ.
Для заказа из разных магазинов нужны хотя бы два поставщика с загруженными каталогами.
Используйте ID предложений из `/products` и ID своего адреса из `/user/contact`.

Почта в разработке выводится в терминал, из которого запущен сервер. Это относится к подтверждению регистрации,
восстановлению пароля и сообщениям о заказах. Настройка реальной отправки SMTP не включена.
Для накладных используется демонстрационный получатель `admin@example.com`.

## Секретный ключ Django

Задайте `DJANGO_SECRET_KEY` через окружение. Если переменная не задана, приложение один раз создаёт
локальный случайный ключ в `orders/.django-secret-key` и использует его при следующих запусках.
Этот файл и `.env` с вариантами `.env.*` исключены из Git. Приложение не загружает файлы `.env`.
Ключи и SMTP-пароли из настроек собственной реализации и учебного примера удалены.
Старые коммиты Git это изменение не очищает; ранее опубликованные действующие реквизиты необходимо отозвать.

## Итоговая проверка пятого этапа

В отдельном терминале из папки `orders`:

```powershell
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py test backend --noinput
python -m pip check
```

Тесты автоматически создают схему в отдельной SQLite-базе с применением миграций и удаляют её после выполнения.
Рабочая база `db.sqlite3`, её пользователи и заказы не изменяются. Письма тестов сохраняются в памяти,
внешние почтовые серверы не используются.

`backend.test_stage5.PurchaseAcceptanceTests` проходит всю цепочку через API: поставщики загружают каталоги,
покупатель регистрируется, берёт токен из сформированного письма, подтверждает email, входит,
покупает товары двух магазинов и получает заказ. Проверяются UTF-8 адреса, обе накладные/подтверждения,
остатки, история заказов, видимость позиций поставщику и переходы до статуса «Доставлен».
Отложенные почтовые обработчики в этом сценарии выполняются после настоящего commit тестовой транзакции.

`ImportCommandAcceptanceTests` отдельно проверяет загрузку приложенного YAML на пустую базу,
повторный импорт без дубликатов и отказ при некорректном файле.

## Границы проверки

Проверка миграций и сценариев использует установленное локальное окружение, не новую загрузку пакетов из интернета.
Нагрузочное тестирование и одновременное оформление заказов несколькими процессами не входят в эти тесты.
Настройки рассчитаны на локальную разработку; публичное развёртывание требует отдельной настройки секретов,
хостов, HTTPS и почты. Асинхронная отправка и повторная доставка писем относятся к расширению с Celery.
